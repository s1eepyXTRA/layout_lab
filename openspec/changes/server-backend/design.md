# Design

## Context

Мотивация — в `proposal.md`. Здесь важно, с чего мы стартуем.

Клиент — набор обычных скриптов, которые `build.py` склеивает в один HTML. Ни npm, ни бандлера, ни
модулей; зависимости между файлами — это порядок в `ORDER`. Всё состояние проходит через одну
функцию `saveState()` и читается при старте в `boot()`; строки загруженных наборов лежат в IndexedDB
(`loadUploaded()`), строки наборов-схем порождаются генератором по `seed`. Расчёт — `runQuery` по
массиву объектов в памяти вкладки.

Серверная часть начата: `kobra/service/backend/app/core.py` — настройки из `KOBRA_*`, модели
метаданных (`kobra_users/connections/datasets/charts/dashboards/settings`), bcrypt, JWT и Fernet для
строк подключения. Поля `owner_login`/`team`/`shared` в моделях совпадают с клиентскими, а
`Chart.viz + params` и `Dashboard.body` повторяют форму клиентских объектов. API, миграций и
LDAP-клиента нет.

## Goals / Non-Goals

**Goals:**

- Одно общее хранилище и проверка прав на стороне, которую нельзя подменить из браузера.
- Переход, который не переписывает клиент: точка входа в хранилище остаётся одна.
- Развёртывание привычным для компании способом: образ, переменные окружения, Helm.
- Формат объектов не меняется — то, что лежит в `localStorage` сегодня, должно без переделки
  ложиться в таблицы.

**Non-Goals:**

- Переносить расчёт на сервер. `runQuery` остаётся в браузере.
- Редактирование одного шаблона вдвоём одновременно. Одновременную правку мы обнаруживаем и
  отклоняем, но не сливаем.
- История версий шаблона и аудит действий.
- Многоарендность сверх нынешней модели «команда + список доступа».

## Decisions

### Монолит: один образ отдаёт и интерфейс, и API

API отдаёт собранный `index.html` как статику. Альтернатива — отдельный контейнер с nginx под
статику — добавляет вторую единицу развёртывания ради файла размером полмегабайта и заводит вопрос
о согласованности версий интерфейса и API. Один образ снимает и то и другое: версия интерфейса — это
версия образа.

### Расчёт остаётся в браузере

Сервер хранит и отдаёт, считает клиент. Альтернатива — считать на сервере поверх SQL — это
фактически другой продукт (им и является целевая BI-система), и она ломает главный путь Кобры:
макет на придуманных данных, которых в базе нет вовсе. Решение имеет понятную границу: когда выдача
перестанет влезать в браузер, расчёт поедет на сервер отдельным изменением.

### Клиент получает адаптер хранилища, а не сетевые вызовы по всему коду

Новый файл `src/storage.js` (в `ORDER` до `app.js`) даёт два режима: локальный — нынешние
`localStorage` и IndexedDB, серверный — API. `saveState()` и `boot()` зовут адаптер. Альтернатива —
расставить `fetch` по местам, где сейчас пишут состояние, — разъедется в первый же месяц, потому что
таких мест станет больше.

Режим выбирается наличием API: офлайн-сборка `kobra.html` всегда локальная, сборка в образе —
серверная. Выбрасывать локальный режим нельзя: офлайн-сборка — единственный способ показать Кобру
там, где ничего не разворачивают.

### Отправка состояния — очередь с дебаунсом, а не вызов на каждое изменение

`saveState()` сегодня синхронный и зовётся отовсюду, включая обработчики перетаскивания. Серверный
режим ставит изменение в очередь (дебаунс порядка секунды), показывает состояние «не сохранено» и
повторяет отправку при обрыве. Альтернатива — await на каждом вызове — сделала бы интерфейс рваным и
потребовала бы переписать все вызовы.

### Одновременную правку ловим версией объекта, а не блокировками

У каждого объекта есть версия; запись принимается, только если клиент видел текущую. Блокировки
(«шаблон занят») требуют снятия зависших блокировок и объяснения человеку, почему он не может
править свой же шаблон с другой вкладки. Слияние правок (CRDT и подобное) несоразмерно задаче.

### Объект клиента хранится целиком в JSON-колонке

В базе у шаблона, графика и набора есть колонка `body` с клиентским объектом как
есть, а в отдельные колонки вынесено только то, что сервер правда запрашивает:
владелец, команда, список доступа, версия, название и время правки.

Так вышло не из лени. Форма клиентского объекта шире, чем казалось при планировании:
у графика есть `spec` (поля ТЗ) и `autoName`, у шаблона — `fromTemplate`, `scheme`,
`crossFilter`. Разложить их по типизированным колонкам можно, но тогда каждая правка
клиента становится миграцией, а запрашивать эти поля на сервере некому: расчёт идёт
в браузере. Цена решения честная: SQL-запросом по содержимому графика не походишь —
придётся лезть в JSON. Когда расчёт поедет на сервер, нужные поля можно будет поднять
в колонки отдельным изменением, данные для этого уже будут.

Из этого следует правило: **сервер не придумывает полей клиентскому объекту и не
теряет чужих**. Всё, что пришло, возвращается обратно; сервер добавляет к ответу
только свои поля — `version`, `ownerLogin`, `team`, `shared`, `updated`.

### Строки загруженных наборов — одна таблица с JSONB

`kobra_uploads.rows(dataset_id, idx, data jsonb)` плюс индекс по набору. Альтернатива — отдельная
типизированная таблица на каждый набор — быстрее для серверных агрегаций, но их у нас нет: строки
всё равно уезжают в браузер целиком. Динамический DDL на каждую загрузку — лишний риск ради выгоды,
которой мы пока не пользуемся. Лимит остаётся прежним (`MAX_UPLOAD_ROWS`).

Наборы-схемы строк не хранят вовсе: в базе лежит описание колонок и `seed`, строки порождает клиент.
Это экономит и хранилище, и трафик, и сохраняет свойство «цифры одинаковы у всех».

### Redis: четыре роли, названные явно

Redis включён в состав сервиса. Чтобы он не стоял «на всякий случай», за ним закреплены конкретные
задачи, и каждая проверяема:

1. **Кэш выдачи** строк и описаний — требование «повторная выдача не пересчитывается заново».
2. **Брокер Celery** для разбора больших файлов и выгрузок — требование «разбор идёт в фоне».
3. **Ограничение частоты** запросов, общее для всех экземпляров сервиса.
4. **Список отозванных сессий** — чтобы выход и отключение сотрудника действовали сразу, а не по
   истечении срока JWT.

Трезво: первые два этапа работают и без Redis (кэш в памяти процесса, разбор синхронный), и именно
поэтому Redis подключается на этапе 2, а не на этапе 1 — чтобы этап 1 не ждал инфраструктуры.
Сервис MUST подниматься при недоступном Redis: готовность считается по базе, а задачи, которым
нужен Redis, отвечают явной ошибкой. Иначе кэш превращается в точку отказа сильнее, чем само
хранилище.

### Сессии: JWT с коротким сроком плюс список отозванных

JWT не отзывается сам по себе, а отзыв нам нужен (увольнение, выход). Поэтому срок жизни короткий,
а отозванные идентификаторы лежат в Redis до истечения срока. Альтернатива — серверные сессии в
базе — это запрос к Postgres на каждом обращении ради того же результата.

### LDAP — на сервере, конфигурация именами FAB

Bind делает сервер (`ldap3`), названия параметров остаются такими же, как в `auth.js`
(`AUTH_TYPE`, `AUTH_LDAP_SERVER`, `AUTH_LDAP_SEARCH`, `AUTH_LDAP_UID_FIELD`,
`AUTH_LDAP_GROUP_FIELD`, `AUTH_ROLES_MAPPING`). Это не косметика: администратор, который настраивал
Superset, настраивает Кобру теми же словами.

### Права: сервер — источник истины, клиент — подсказка

`canView`/`canEdit`/`canShare` остаются в клиенте, чтобы прятать кнопки, но решение принимает
сервер. Правила переносятся в одну функцию серверного кода — ровно так же, как сейчас они живут в
трёх функциях клиента. Расхождение правил ловится тестами на сервере.

### Миграции — отдельным шагом до старта

`alembic upgrade head` выполняется job-ом в Helm и в entrypoint окружения разработки. Альтернатива —
`create_all` при старте — не переживает ни одного изменения схемы.

## Risks / Trade-offs

- **Состояние становится асинхронным** → очередь отправки с дебаунсом, явный признак «не
  сохранено», версия объекта против перезаписи. Это самая опасная часть работы: ошибки здесь
  выглядят как «пропали правки».
- **Выдача строк по сети** (до `MAX_UPLOAD_ROWS` на набор) → лимит, сжатие, кэш; при росте объёмов
  — расчёт на сервере отдельным изменением.
- **Два режима хранения** (локальный и серверный) → двойное тестирование. Снижаем тем, что режимы
  разделены одним адаптером, а не разбросаны по коду.
- **Два места с правилами прав** → сервер решает, клиент показывает; тесты на серверные правила
  обязательны.
- **Redis как новая зависимость** → сервис поднимается без него с деградацией, готовность считается
  по базе.
- **Секреты в окружении** (ключ шифрования, токен) → Secret в Helm, явное предупреждение при
  незаданном ключе — оно уже есть в `core.py`.

## Migration Plan

1. **API и метабаза.** Миграции, вход по базе, CRUD шаблонов, графиков и наборов-схем. Клиент —
   адаптер хранилища и серверный режим. Данные не переносятся: у кого что лежит в браузере, то и
   лежит.
2. **Загруженные данные и фон.** Строки в Postgres, разбор файла задачей Celery, кэш выдачи, Redis
   появляется здесь.
3. **LDAP и отзыв сессий.** Вход через каталог, роли из групп, список отозванных сессий.
4. **Упаковка.** Dockerfile (сборка интерфейса + API в одном образе), `docker compose` для
   разработки, Helm-чарт с секретами, job миграций и пробами.

Перенос того, что люди уже собрали: выгрузка `.kobra.json` из локального режима и импорт в
серверном. Отдельного миграционного инструмента не делаем — объектов немного, а формат один и тот
же.

Откат: предыдущий образ плюс `alembic downgrade` до предыдущей ревизии. Поэтому каждая миграция
обязана иметь работающий `downgrade`, а необратимые шаги (удаление колонок) разносятся на два
релиза.

## Open Questions

- Где живут настройки доступа к модели (`kobra.ai.cfg`): остаются в браузере у каждого или
  становятся настройкой сервиса, одной на всех. Ответ не меняет ни спеки, ни этапы — решаем на
  этапе 1, когда появится экран настроек сервиса.
- Нужна ли выдача строк постранично или достаточно отдавать набор целиком с лимитом. Зависит от
  первых реальных файлов; на схему базы не влияет.
