# Design

## Context

Зачем — `proposal.md`. Что должно получиться — `specs/dashboard-templates/spec.md` и
`specs/server-storage/spec.md`.

Это изменение стоит **после** `client-load-scale`: там список начинает отдавать краткую форму и
принимать постраничность, здесь поверх этого появляются поиск, «только мои» и показ автора правки.
Делать поиск до краткой формы бессмысленно — сервер всё равно отдавал бы тела.

Как сейчас:

- Список объектов возвращается целиком (`objects.py`, `list_objects`), фильтрация по видимости — в
  SQL, но ни поиска, ни постраничности нет.
- `updated` и `updatedBy` приезжают в каждом ответе и нигде не показаны.
- Отказ по версии (409) обрабатывается в `storage.js` переводом состояния в `conflict`, а в шапке
  появляется «перечитать» (`reloadFromServer` в `app.js`). Чужая версия в ответе не приходит.

## Goals / Non-Goals

**Goals:**

- Найти свой шаблон среди чужих за одно действие.
- Увидеть, кто правил, не открывая объект.
- Не терять свою правку молча при расхождении.

**Non-Goals:**

- Полная история версий объекта с возвратом к любой. Это отдельная и большая задача: хранить тела
  всех версий, показывать разницу, решать, кто может откатывать. Сейчас речь только о последней
  правке — её сервер уже знает.
- Слияние двух правок. Шаблон — это дерево блоков, и автоматическое слияние даст результат, которого
  не хотел никто. Человек выбирает чью версию, а не получает смесь.
- Поиск по содержимому (по названиям блоков, по колонкам). Поиск по названию закрывает случай «где
  мой шаблон»; поиск по содержимому требует отдельного индекса.
- Фильтры по команде и по дате. Сначала поиск и «только мои»; остальное — когда попросят.

## Decisions

### Поиск считает сервер, а не клиент

`?q=` и `?mine=1` поверх уже существующего фильтра видимости, плюс `limit`/`offset` из
`client-load-scale`. Фильтровать скачанный список нельзя по той же причине, по которой список стал
кратким: скачивать всё, чтобы показать десять, — это и есть исходная проблема.

Поиск — по названию, без учёта регистра, подстрокой. Для тысяч объектов этого достаточно и индекс по
названию решает; полнотекстовый поиск здесь был бы оружием не по цели.

### «Только мои» — это владелец, а не доступ

Переключатель оставляет объекты, где человек `ownerLogin`. Объекты, которыми с ним поделились, — не
«мои»: они чужие, и человек их различает. Состояние переключателя помнится в личных настройках, а не
в адресе: человек один раз выбирает, как ему смотреть, и возвращается к тому же.

### Отказ по версии возвращает чужую версию и автора

Сейчас 409 говорит только «версия не та». Добавляем в ответ версию, время и автора чужой записи —
тогда диалог может сказать «Пока вы правили, Иванов сохранил свою версию 12 минут назад» и дать два
действия: перечитать чужое (как сейчас) или записать своё поверх.

Запись поверх идёт тем же маршрутом с явным указанием, что человек знает о расхождении — иначе
отличить «осознанно поверх» от «клиент не заметил отказа» нельзя, а это разные вещи.

Тело чужой версии в отказ не кладём: оно может быть большим, а для выбора достаточно знать, кто и
когда. Кому нужно посмотреть — перечитывает.

### Подпись правки — на карточке, одной строкой

«Правил Иванов · 12 минут назад», с полной датой в подсказке. Своё имя не пишем: «правил я» занимает
место и ничего не сообщает — для своих объектов остаётся только время.

## Risks / Trade-offs

- **Поиск по подстроке на тысячах объектов без индекса будет медленным** → индекс по названию в
  миграции; сравнение без учёта регистра приводится к одному виду.
- **«Только мои» спрячет объект, которым поделились, и человек решит, что он пропал** → счётчик
  показывает оба числа: сколько моих и сколько всего видно.
- **Выбор «записать своё поверх» уничтожит чужую правку** → в диалоге сказано, чья правка будет
  потеряна и когда она сделана; это именно выбор человека, и он должен быть осознанным, а не
  удобным.
- **Постраничность и поиск разойдутся с клиентским кэшем списка** → список перезапрашивается при
  смене запроса; держать клиентский кэш страниц не нужно.
