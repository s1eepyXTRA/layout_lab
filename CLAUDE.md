# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## О проекте

«Кобра» — браузерный прототип конструктора дашбордов в стиле Superset. Весь код живёт в `kobra/`,
собирается в один HTML-файл. Ни npm, ни бандлера нет: `src/*.js` — это обычные скрипты
с глобальными функциями, которые `build.py` склеивает в `<script>` внутри HTML. Тесты есть, но
только на ядро и тоже без зависимостей — `node test/run.js`. Данные и дашборды
хранятся только в браузере (localStorage + IndexedDB). Интерфейс и весь код на русском языке
(комментарии, названия, сообщения об ошибках) — продолжай в том же стиле.

**Как это называется.** В интерфейсе то, что человек собирает и правит, — **шаблон** (будущего
дашборда): «Новый шаблон», «Свойства шаблона», раздел «Шаблоны». В коде, состоянии и маршрутах это
по-прежнему `dashboard` — `STATE.dashboards`, `#/d/<id>`, `dashboard.js`: переименование сломало бы
сохранённые состояния и ссылки. Значит, новые **строки интерфейса** пишутся про шаблон, а код,
комментарии и спеки остаются на дашборде. Два исключения в интерфейсе: ТЗ (`spec.js`) уезжает
аналитику, и в самом документе речь о дашборде, который по шаблону построят; «макет» — не синоним
шаблона, а пометка, что цифры придуманы. «Готовый шаблон» — скелет из каталога (`templates.js`), с
которого шаблон начинают.

## Команды

```bash
cd kobra
py build.py           # → build/index.html  (библиотеки с CDN jsdelivr, нужен интернет)
py build.py offline   # → build/kobra.html  (всё внутри файла, открывается двойным щелчком)
node service/tools/export_demo.js   # перегенерировать service/backend/app/demo/*.csv.gz из src/data.js
node test/run.js                    # тесты: ядро, синтаксис всех файлов, свежесть build/
node test/run.js auth.test.js       # один файл
npx -p typescript@5.6.3 tsc -p kobra/jsconfig.json   # проверка типов по JSDoc (из корня репозитория)
```

На этой машине работает `py`, а не `python3` (`python`/`python3` — заглушки Microsoft Store и печатают только «Python»); в README команды записаны как `python3`.

Ядро проверяется тестами (`test/`), интерфейс — руками: пересобрать и открыть `build/index.html`.
Три грабли, на которые раньше наступали молча, теперь падают сразу: файл в `src/`, забытый в `ORDER`
(проверяет сам `build.py` перед сборкой), несобранный `build/` после правки `src/` и сломанный
синтаксис (`test/build.test.js`).
`test/load.js` грузит `src/*.js` в контекст `vm` тем же порядком, что `build.py`, и отдаёт их
глобальные функции. Важная тонкость: `const` и `let` верхнего уровня живут в лексической области и
**не становятся свойствами** `globalThis`, поэтому снаружи их не видно — нужные имена перечислены в
`BRIDGE` и прокидываются геттерами. Объявления `function` уже глобальные, и мост их не трогает:
геттер поверх такого имени начинает звать сам себя.
`.claude/launch.json` поднимает `py -m http.server 8777 --directory kobra/build` — приложению нужен http,
потому что оно ходит по `history.pushState`. В скрытом окне браузера `requestAnimationFrame` не срабатывает,
а `paintGrid` отдаёт туда и раскладку, и первую отрисовку графиков — поэтому в свёрнутом окне сетка
остаётся пустой; это не поломка, достаточно показать окно.
Файлы в `build/` закоммичены, поэтому после правок в `src/` **нужно пересобрать оба варианта**,
иначе репозиторий окажется в рассинхроне.

## Спецификации (OpenSpec)

Планы будущих изменений живут в `openspec/` (CLI `openspec`, версия 1.14.3, схема `spec-driven`,
артефакты пишутся по-русски, структурные заголовки и SHALL/MUST — по-английски).
`openspec/specs/` — спецификации уже реализованного, `openspec/changes/<имя>/` — план
изменения: `proposal.md` (зачем), `specs/<способность>/spec.md` (что система должна делать),
`design.md` (как и почему именно так), `tasks.md` (шаги).

```bash
openspec list                        # изменения в работе и прогресс по задачам
openspec show <имя> --type change    # посмотреть изменение целиком
openspec validate <имя>              # проверить структуру перед коммитом
openspec status --change <имя>        # какие артефакты готовы
```

Рабочий процесс — через скиллы в `.claude/skills/openspec-*` и команды `/opsx:*`: `propose` заводит
изменение и пишет артефакты, `apply` реализует, `archive` переносит спецификации в `openspec/specs/`.
Главное правило: `propose` — только планирование, код в этом шаге не трогают.

Незакрытых изменений нет; реализованное описано в `openspec/specs/`: `dashboard-templates`,
`guided-editing`, `mockup-mode`, `dashboard-assistant`. Перед правкой этих частей читай спеку
способности, а историю решений — в `openspec/changes/archive/<дата>-<имя>/design.md`: там
зафиксировано, почему выбран именно такой путь, и чего делать не надо.

## Сборка и порядок файлов

`build.py` склеивает `src/styles.css` + `src/*.js` в порядке `ORDER`:
`data → engine → ui → auth → store → router → grid → viz → app → dashboard → explore → datasets →
schema → autodash → templates → guided → assistant → share → spec`. Порядок важен —
это и есть вся система зависимостей: верхнеуровневые `const` видят только то, что объявлено раньше
(объявления функций поднимаются, поэтому вызывать функцию из более позднего файла можно).
Новый файл в `src/` не подхватится, пока его не добавят в `ORDER`.

ECharts, marked и DOMPurify подключаются в `<head>`; SheetJS и PapaParse (Excel/CSV) грузятся лениво
через `loadScript()` — в офлайн-сборке `build.py` патчит `loadScript`, чтобы он возвращал уже
вшитые библиотеки. Точка входа — `boot()` в `app.js`, вызывается из инлайн-скрипта в HTML.

## Типы (JSDoc, без TypeScript)

Типы описаны в JSDoc и проверяются компилятором TypeScript, но **переезда на TypeScript нет и не
планируется**: сборка — это конкатенация скриптов в один `<script>`, а `tsc` требует npm-тулчейна и
модулей, то есть бандлера. `checkJs` же работает в «скриптовом» режиме и понимает глобальные функции
между файлами — ровно наш случай. Редактор проверяет на лету, разово всё целиком:
`npx -p typescript@5.6.3 tsc -p kobra/jsconfig.json` (ноль ошибок — это состояние, которое нужно
держать).

- `src/types.js` — формы, которые ездят между файлами: `Dataset`, `Column`, `MetricRef`, `QuerySpec`,
  `QueryResult`, `Chart`, `Dashboard`, `AppState`, `User`, `VizDef`, `VizCtx`. Локальные объекты не
  описываем: вывод типов справляется сам, а лишние `@typedef` устаревают молча. Файл в `ORDER` и
  едет в сборку — в нём только комментарии.
- `types/globals.d.ts` — единственный файл на TypeScript, и он ничего не исполняет: объявления для
  ECharts, marked, DOMPurify, SheetJS и PapaParse. Типов у них нет намеренно, `@types/*` потянули бы
  зависимости.
- `jsconfig.json` — `strictNullChecks` выключен намеренно: код DOM-овый и нигде не проверяет `null`,
  строгость утопила бы сигнал в шуме. Ловим дешёвое: опечатки в полях, неверную арность,
  несуществующие имена.

Параметр-объект описывается только у **именованного** параметра: JSDoc не умеет называть
деструктуризацию, поэтому `function f(a, opts = {})` и `const { x } = opts;` внутри, а не
`function f(a, { x } = {})`.

Что это уже поймало: вызов `send` из области видимости, где его нет (кнопка «Собрать по брифу»
сохраняла бриф и молча ничего не отправляла), одиннадцать вызовов `tuneTouch(id)` с аргументом,
который после рефакторинга никто не читает, вычитание логических значений в сортировке и
`isNaN(дата)` вместо `isNaN(дата.getTime())`.

## Архитектура

### Движок (`engine.js`)

Всё считается в памяти по массиву JS-объектов — SQL нет.

- `DS` — глобальный реестр наборов данных: `{id, name, columns:[{key,label,type}], metrics, rows, mainDttm}`.
  Тип колонки — `'string' | 'number' | 'date'`; даты всюду хранятся как UTC-миллисекунды, форматируются
  через `fmtDate`/`truncTime`/`shiftTime` (все по UTC — так расчёты не зависят от часового пояса).
- `runQuery(ds, spec)` — единственный способ получить данные для графика.
  `spec = {filters, groupby:[{col,grain}], metrics:[metric], orderby:[{key,desc}], limit}`,
  ответ — `{rows, dims, mets, filteredCount}`, где `dims[].key` = `col` или `col__grain`,
  а `mets[].key` = человекочитаемая подпись метрики (по ней же и достаются значения из `rows`).
- Метрика в параметрах графика: `{kind:'saved', key}` (ссылка на `ds.metrics`) либо
  `{kind:'simple', agg, col}`. Сохранённая метрика хранит `expr`: `{type:'simple', agg, col}` или
  `{type:'ratio', num, den, mult}` — отношения считаются как два аккумулятора, а не делением готовых
  агрегатов, поэтому «Маржинальность» правильна на любом уровне группировки.
- Агрегации собираются в `makeAcc`/`compileMetric` как тройки `{init, add, fin}` — это позволяет
  обойти строки один раз на весь запрос. Новая агрегация добавляется в `AGGS` + `makeAcc`.
- Фильтр — `{col, op, val}`, `op` из `FILTER_OPS` плюс особый `time_range`
  (`{preset, from, to}`, см. `TIME_PRESETS`/`resolveTimeRange`). **Относительные периоды считаются
  от последней даты в данных**, а не от «сегодня», — демо-данные заканчиваются 31.08.2026.

### Реестр визуализаций (`viz.js`)

`VIZ[type] = { label, en, icon, desc, controls, defaults(ds), render(root, ctx) }`, порядок в галерее —
`VIZ_ORDER`. 13 типов; `line/area/bar` построены на общих `xyControls`/`xyDefaults`/`renderXY`.

- `controls` — декларативная схема: секции `{title, tab:'data'|'view', controls:[...]}`, где контрол
  это `{key, type, label, def?, showIf?(p, ds), ...}`. Типы контролов рендерит `buildControl` в
  `explore.js` (`column`, `columns`, `metric`, `metrics`, `filters`, `timerange`, `grain`, `select`,
  `segment`, `check`, `number`, `scheme`, `format`, …). Общие контролы — `C_TIME`, `C_FILTERS`,
  `C_SCHEME`, `C_FORMAT`, `C_LEGEND`, `C_LIMIT`.
- `render(root, ctx)` получает `ctx = {ds, params, colors, filters, setData, cross, crossActive}`:
  `params` — это `defaults(ds)` поверх сохранённых, `filters` уже собраны из ad-hoc фильтров графика,
  его периода и фильтров дашборда (`buildChartFilters`). Обязанности рендерера: вызвать `ctx.setData(res)`
  (питает пункт «Посмотреть данные»), отрисовать через `ecInit(root)` или DOM, повесить клик
  на `ctx.cross([...filters])` для кросс-фильтрации и приглушить невыбранное (`crossSet`/`dimInactive`).
  Исключения ловит `renderChart`, так что внутри можно смело бросать понятные ошибки.
- Новый тип графика = запись в `VIZ` + ключ в `VIZ_ORDER` + иконка `v_*` в `ICONS` (`ui.js`).

### Состояние и страницы

- `STATE` (`app.js`) — весь пользовательский мир: `{v:1, charts, dashboards, datasets, dsMetrics, theme}`,
  пишется в localStorage под `kobra.state.v1` через `saveState()`/`saveSoon()`. При смене формы данных
  поднимай `v` — `boot()` при несовпадении пересоздаёт состояние из `seedState()`.
- `duplicateDashboard(id)` делает **самостоятельную** копию: свои графики (новые id) и свой
  скрытый набор макета. Общие графики означали бы, что правка копии меняет оригинал, а общий
  скрытый набор — что удаление одного дашборда уносит данные у второго. Переписка с ассистентом и
  владелец не копируются: копия достаётся тому, кто копировал (`authStampAll` из `saveState`).
- `seedState()` — демо-дашборд «Продажи розничной сети» целиком в коде: 23 графика и 4 вкладки заданы вызовами
  `mk(...)`/`ch(...)`. Это и эталонный пример всех параметров графиков, и то, что восстанавливает
  «Вернуть демо-дашборд».
- Роутер — на хэше, `router.js`: `#/dashboards`, `#/d/<id>?edit=1`, `#/charts`,
  `#/explore/<id|new>?ds=&viz=&back=`, `#/data[/<id>]`. Каждая страница-рендерер возвращает функцию
  очистки (её зовут при следующем переходе — там снимают `ResizeObserver` и `dispose()` у ECharts).
- `grid.js` — сетка 12 колонок (`G_COLS/G_ROWH/G_GAP`), `compactLayout()` и `itemDefaultSize()`.
  Ею пользуется и страница дашборда, и генераторы (черновик по набору, сборка из шаблона).
- `dashboard.js` — страница: перетаскивание, одноколоночная раскладка при ширине < 760, режимы
  правки. Зелёной (primary) в шапке **макета** стоит «Названия и разрезы», а не «Редактировать»:
  макет правят подписями, конструктор нужен аналитику. У дашборда на настоящих данных наоборот.
  Чужой шаблон вместо тупика «нельзя править» предлагает «Сделать копию». Правка идёт **по живому состоянию**, а «Отменить» возвращает снимок (`store.js`);
  фильтры — через `pending` + кнопку «Применить».
  Кросс-фильтры живут в `crossMemory[dashId]` (не сохраняются), по одному набору на график-источник.
- `datasets.js` — загрузка CSV/Excel: парсинг → угадывание типов (`guessType`, `parseNumberLoose`,
  `parseDateLoose`) → предпросмотр → `saveUploaded()`. Метаданные идут в `STATE.datasets`,
  строки — в IndexedDB (`idb`, ключ `rows:<id>`), лимит `MAX_UPLOAD_ROWS`.
  Пользовательские метрики встроенных наборов хранятся отдельно в `STATE.dsMetrics` и
  накладываются в `applyDsOverrides()`, потому что сами наборы генерируются заново при каждом запуске.
- `data.js` — детерминированная генерация демо-данных (`mulberry32` с фиксированным seed), так что
  цифры одинаковы у всех. Описания наборов — в `BUILTIN_DATASETS`. Изменил генерацию — перезапусти
  `service/tools/export_demo.js` (он читает `src/data.js` через `eval`, то есть файл должен
  оставаться валидным скриптом без `export`).

### Состояние и откат (`store.js`)

Откат был написан трижды: снимок предложения у AI-ассистента, снимок затронутых графиков и набора в
простой правке, клон дашборда в конструкторе. Все три решали одну задачу и ломались по отдельности.
Теперь он один: `snapState(label)` кладёт клон всего `STATE` в стопку на `UNDO_MAX`, `undoState(snap)`
возвращает его, `canUndo(snap)` отвечает про **конкретный** снимок, `mutate(label, fn)` — правка с
откатом при исключении. Снимок маленький: строки загруженных наборов лежат в IndexedDB, строки
макетов порождаются по схеме, так что в `STATE` только дашборды, графики и описания наборов.

Два правила, без которых это не работает:

- `undoState` восстанавливает **в те же объекты** (`restoreMap`), а не подменяет `STATE`. Открытая
  страница держит ссылки на свой дашборд и его графики; подмена объекта оставила бы её рисовать то,
  чего в состоянии уже нет, а у «Отменить» сбилась бы точка отсчёта.
- `syncDatasetsFromState()` пересобирает `DS` под восстановленные метаданные: строкам схемы нужен
  новый проход генератора (seed тот же — цифры те же), у загруженных наборов строки остаются из
  памяти. Без этого после отката блоки смотрят на колонки, которых уже нет.

`canUndo(null)` — это **нет**: когда-то он отвечал «да, стопка не пуста», и снимок не снимался вовсе,
а откат молча ничего не делал.

### Наборы-схемы (`schema.js`)

Набор, у которого есть только описание колонок: строки придумываются по `schema`
(`{seed, rowCount, dateFrom, dateTo, columns:[{key,label,type,values?,min?,max?,decimals?}]}`).
Такой набор помечен `kind: 'schema'` и **не хранится в IndexedDB** — `loadUploaded()` при старте
зовёт `generateSchemaRows(meta.schema)`, поэтому цифры одинаковы при каждом открытии и на любой машине
(один и тот же `seed`). Период дат фиксируется в схеме при создании: иначе строки менялись бы каждый день.
Генератор намеренно даёт длинный хвост (большинство значений у нижней границы, в максимум упирается
около 1 % строк) и разный масштаб по первой текстовой колонке, чтобы макет выглядел как живые данные.
Тип и правдоподобные значения колонки угадываются по её названию (`SCHEMA_HINTS`, `guessSchemaCol`),
а «, ₽» или «, шт.» в конце названия не считаются отдельной колонкой (`parseColumnNames` + `UNIT_TAIL`).
Рядом с названием такого дашборда стоит ярлык «Макет» — без него макет легко принять за отчёт;
большой полосы наверху нет, она занимала пол-экрана ради одного слова.

### Черновик дашборда (`autodash.js`)

Кнопка «Собрать черновик дашборда» на странице набора (`openAutoDashDialog`): по колонкам набора
создаются графики и дашборд, дальше человек только правит готовое. `buildAutoDash(ds, opts)` отдаёт
план — список `{name, viz, params, size}` и нативные фильтры, `createAutoDash(ds, title, opts)`
кладёт графики в `STATE.charts`, дашборд в `STATE.dashboards` и возвращает его id.
Параметры графиков всегда собираются поверх `VIZ[type].defaults(ds)`, поэтому новый тип графика и
изменившиеся дефолты не разъезжаются с генератором. Главная метрика выбирается по `autoMetricRank`:
деньги (формат `rub*` или `₽`/«руб» в подписи) → прочие числа → проценты → `COUNT(*)` в крайнем
случае. Разрезы — текстовые колонки с мощностью 2…`AUTO_DIM_CARD_MAX` (`autoDims`, идентификаторы
отбрасываются). Названия графикам даёт `autoTitleBy` через падежи `autoDative` («Выручка по
филиалам»), что не склонилось — печатается через двоеточие. Раскладка считается по той же сетке
12 колонок слева направо, размеры — из плана или `itemDefaultSize`, в конце `compactLayout`.
Этот модуль — единственное место, где правят состав черновика; новый блок = запись в `buildAutoDash`
плюс галочка в `openAutoDashDialog`.

### Готовые шаблоны (`templates.js`)

Шаблон — скелет из уровней детализации, разложенных по вкладкам: сводка (что происходит), разбор
(за счёт чего), документы (исходные строки). Описывается данными: `{id, name, dash, desc, examples,
need, derived, levels: [{id, blocks}], demo}`, где блок ссылается на **роли полей** (`TPL_ROLES`), а
не на колонки: `{viz, metric: 'money', by: 'dim1', need: [...], params, size}`. Вид процесса (продажи,
воронка, план-факт, поток обращений) меняет только наполнение уровней — скелет один на всех.

У шаблона **два названия**. `name` — название приёма («Факт против плана»): так человек видит, что
выбирает скелет, а не чужой готовый отчёт. `dash` — отчётное название («План и факт»), его получает
собранный дашборд, вступительный блок и предпросмотр; берётся через `tplDashName(tpl)`, который
падает на `name`, если `dash` не задан. `examples` — живые примеры, для чего приём бывает полезен;
печатаются в карточке каталога строкой «Например: … · …».

Колонки под роли подбирает `pickRoles(ds)` из `autodash.js` — **единственная** точка подбора на весь
продукт, ею же пользуется черновик по набору. Нужно новое правило угадывания (этап воронки, план) —
дописывать туда, а не в `templates.js`, иначе эвристики разъедутся.

На карточке каталога — миниатюра раскладки (`tplThumb`): плитки первого уровня в тех же местах, где
их потом расставит `tplLayout`, с иконкой вида внутри. Считается **по описанию блоков**, без набора
данных, поэтому миниатюра есть и у того, кто ещё не принёс свой файл; вступительный блок в неё не
попадает — серая полоса во всю ширину ничего не говорит. Общий вид (`dash-thumb`) взят у карточек
списка шаблонов, чтобы не плодить второй способ рисовать то же самое.

Карточки в каталоге фильтруются **приёмами** (`TPL_TAGS` + `tags` у шаблона): динамика, состав,
этапы, план-факт. Человек приходит с вопросом «как показать динамику», а не с названием шаблона;
чипы переводят выбор на этот язык. Новый шаблон без `tags` виден только под «Всё» — не забывать.

`templateFits` говорит, каких обязательных ролей не хватает; `buildFromTemplate` собирает план
уровней и пропускает блоки, чьи роли пустые; `createFromTemplate` пишет графики и дашборд в `STATE`
и запоминает в нём `fromTemplate: {tplId, datasetId, levels, roles}`. Параметры графиков всегда
кладутся поверх `VIZ[viz].defaults(ds)`.

Своего механизма перехода между уровнями нет и быть не должно: клик по графику ставит кросс-фильтр,
который и так действует на весь дашборд, вкладку человек переключает сам, а на первом уровне стоит
подсказка текстом. Правило шире одного случая — взаимодействия, которые увидит зритель готового
отчёта, ограничены возможностями целевой BI-системы (Superset), иначе макет обещает то, чего
аналитик не сможет сделать. На средства самого конструктора (каталог, подбор ролей, простая правка,
выгрузка ТЗ) это ограничение не распространяется.

Производные показатели (средний чек, выполнение плана) объявляются в `TPL_DERIVED` как отношение
ролей и **дописываются в набор**, если их там нет. Поиск существующего идёт по канонической формуле
(`exprKey` сортирует ключи), а не по названию: иначе встроенный «Средний чек» не находится из-за
порядка полей и метрика задваивается. Части отношения — пары `{agg, col}` без поля `type`.

Предпросмотр (`templatePreview`) строит временный набор-схему по `demo` и дашборд с пометкой
`preview: true`; ни то ни другое не пишется в `localStorage`, а `purgePreviews()` в `route()`
убирает их при уходе со страницы. У такого дашборда своя шапка (ветка `D.preview` в `paintHead`,
`dashboard.js`): прилипающая полоса с заметным возвратом в каталог и кнопкой «Выбрать этот шаблон»,
обычных кнопок правки там нет — дашборд всё равно сейчас выбросят, а сохранить его некуда, набор
`tpl_preview` в `localStorage` не живёт. Откуда человек пришёл, помнят `previewBack` и `previewDs`:
из каталога по своему набору возврат приводит обратно к нему, а не на общий список.

### Макет без данных

Главный путь продукта: дашборд-макет, за которым стоит **скрытый набор** — обычный набор-схема с
полем `owner: <id дашборда>`. Такой набор не попадает в `visibleDatasets()` (список данных, выбор
при создании графика, каталог), удаляется вместе с дашбордом (`dropOwnedDatasets()` в `app.js`) и
подчищается при старте, если дашборда уже нет.

`createMockup(tpl, {title, levels})` в `templates.js` порождает набор по описанию `demo` шаблона
(или по нейтральным `MOCKUP_NEUTRAL_COLS`, когда шаблона нет) и собирает дашборд обычным
`createFromTemplate`; `emptyMockup` делает пустой макет без блоков. Блоки добавляются видом
визуализации: `MOCKUP_BLOCKS` описывает виды, `mockupBlockOptions(ds)` отбирает те, что на этих
данных соберутся (воронке нужен этап), `createMockupChart` создаёт блок. Подменять невозможный блок
другим нельзя — человек выбрал вид и должен получить его либо отказ.

Единица измерения прячется в самом формате числа: `'suffix:шт.'` (`fmtSuffix`, `withSuffix`,
`formatLabel` в `engine.js`). Так она доезжает до осей, легенд, подсказок и ячеек, потому что все
они форматируют через `fmtNum`, и не требует правки тринадцати типов графиков. С единицей число не
сокращается: иначе «млн ₽» в единице давало «1,2 млн млн ₽».

### Простая правка (`guided.js`)

Режим `#/d/<id>?tune=1`: правятся только название блока и разрез, без конструктора. Своего формата
нет — меняются обычные графики, поэтому отказ восстанавливается из снимка затронутых графиков
(`tuneBackup` в `dashboard.js`), а не из клона дашборда.

На макете правятся ещё и данные: название показателя и единица пишутся в метрику скрытого набора
(`guidedSetMetricLabel`, `guidedSetSuffix`), а число категорий и их названия — в `values` колонки
схемы с перегенерацией строк тем же seed (`guidedSetCats`). Поэтому переименование видно во всех
блоках сразу; `migrateFilterValues` в `dashboard.js` переносит выбранное в фильтрах по позиции.
Отказ от правки восстанавливает и графики, и набор (`tuneBackup`, `tuneDsBackup`). У настоящих
наборов (`isMockupDs` ложно) правятся только подписи блоков.

Разрезы блока описаны таблицей `GUIDED_DIMS`: по записи на вид визуализации, в записи — слоты
параметров (`x_col` + `series_col`, `groupby[0]` + `groupby[1]`, `rows[0]` + `cols[0]`, `y_col` +
`x_col` у тепловой карты). Их **до двух**: столько, сколько умеет сам график. `optional: true` —
слот, который человек включает кнопкой и убирает крестиком; `guidedDimSlots(ds, chart)` отдаёт
заполненные слоты и те, которые можно включить, а `guidedParamGet/Set` знают про запись
`groupby[1]`. Нет записи в `GUIDED_DIMS` — разрез у этого типа не меняется; у таблицы в режиме
исходных строк разрезов нет вовсе. Слот с датой показывает не выбор колонки, а шаг времени
(`GUIDED_GRAIN`, таблица `TIME_GRAINS`); у большого числа с трендом заголовок пишется «за месяц», у
графиков — «по месяцам» (`GUIDED_FOR`/`GUIDED_BY`). Заголовок пересобирается через `autoTitleBy`
только у графиков с признаком `autoName` — его ставят генераторы (`templates.js`, `autodash.js`) и
снимает любое ручное переименование, в том числе в конструкторе.

На макете каждый разрез правится по отдельности: название колонки схемы, число категорий, их имена и
форма распределения (`guidedCats`/`guidedSetCats`/`guidedRenameDim`/`guidedCycleSpread` — все по
ключу колонки, а не по графику). Второй разрез берёт свободную текстовую колонку схемы, а если все
заняты — `guidedAddMockDim` дописывает новую и пересчитывает строки. У настоящего набора (включая
загруженный CSV) разрез выбирается из его же колонок того же типа, занятые другим разрезом того же
блока не предлагаются, а подписи и категории не правятся — это данные, а не макет.

Высота полосы правки измеряется (`measureTuneRows` в `dashboard.js`): поля переносятся по ширине
плитки, поэтому угадать её нельзя — после раскладки полоса измеряется и, если число рядов изменилось,
раскладка повторяется. Иначе второй разрез наезжает на график.

### AI-ассистент (`assistant.js`)

Панель на дашборде (`renderAssistant`), которую открывают кнопкой в шапке; состояние открыт/закрыт лежит в
`localStorage` под `kobra.ai.open`, переписка — в `D.chat` с пределом `AI_MAX_MSGS` и пометкой
`chatTrimmed`, когда старое вытеснено.

AI-ассистент доступен во всех трёх режимах дашборда — просмотр, простая правка и конструктор
(`?edit=1`), куда ведёт «Начать с нуля»; переключает его один `aiToggle`. Кнопка на экране одна:
`aiBtnInGrid()` отдаёт true, когда в конструкторе открыта пустая вкладка, — тогда кнопка стоит на
самой вкладке, а в шапке её нет. У кнопки свой класс `.btn.ai` (цвета `--accent`): её ищут глазами,
и от обычных кнопок она должна отличаться; иконки нет — змея осталась только логотипом. Справа помещается одна
колонка, поэтому в конструкторе панель AI-ассистента встаёт на место палитры блоков (`paintAi` прячет
`.edit-panel`), а состояние открыт/закрыт там не запоминается — иначе конструктор открывался бы с
AI-ассистентом вместо палитры. В конструкторе `D` — это черновик, и всё, что AI-ассистент пишет в дашборд
(блоки, бриф, переписка, название), живёт в черновике: сохраняется по «Сохранить» и пропадает по
«Отменить». Поэтому `snapshotForAi` снимает черновик, а не `STATE.dashboards[id]`, и откат в
конструкторе возвращает черновик на месте, не выходя из правки. Графики и придуманный набор лежат
**вне** черновика, так что `cancelEdit` доделывает за него: удаляет созданные AI-ассистентом графики,
возвращает изменённые и восстанавливает набор из того же снимка. В `.kobra.json` переписка не уезжает (вырезается в
`collectRefs`).

`aiContext(D, ds, {samples})` — **единственное** место сборки отправляемого: бриф, колонки с типами,
показатели с формулами, состав дашборда. Строк там нет, пока человек не разрешил их галочкой на один
запрос (`AI_SAMPLE_ROWS`), и весь запрос целиком показывается кнопкой «Что уйдёт». Добавлять поля в
запрос мимо этой функции нельзя — иначе политика перестанет быть проверяемой. Текст запроса собирает
`aiPrompt(q, ctx)`: задача, бриф и контекст разделены строками `=== … ===`, иначе модель отвечает на
бриф вместо задачи.

Бриф — первый диалог AI-ассистента: форма из `AI_BRIEF_FIELDS` (название, проблемы, показатели,
проваливаться ли до документов, плюс необязательные разрезы, период, сравнение, кто смотрит).
Ответы лежат в `D.chatBrief` и уходят с **каждым** запросом (`aiBriefLines`), отказ — в
`D.chatBriefSkipped`: форму закрывают крестиком, если макет уже собран и нужно только дополнение.
Название из брифа становится названием дашборда (`api.renameDash`), а сам бриф печатается в ТЗ
разделом «Зачем этот дашборд» (`buildSpecMd`) — он и есть требования, которых в составе блоков не
видно.

Транспорт — OpenAI-совместимый `/chat/completions` (`aiAsk`), адрес, модель и токен из настроек
(`kobra.ai.cfg`): личный эндпоинт сегодня, шлюз компании завтра, код тот же. Ошибки разделены по
видам (`no_access`, `limit`, `network`, `parse`); запрет по CORS браузер отдаёт как сетевую ошибку,
отличить их нельзя. Второй транспорт — перенос вручную: «Скопировать запрос» и «Вставить ответ»,
он работает всегда и в офлайн-сборке остаётся единственным.

Ответ разбирается `aiParse`: неизвестные виды блоков отбрасываются, описание набора превращается в
схему (`aiSchemaFrom`) — строки модель не присылает, их порождает `schema.js`. Применение идёт
только по подтверждению, перед ним снимается `aiSnap` с клоном дашборда, **копиями его графиков** и
метаданными набора: графики лежат отдельно от дашборда и правятся на месте, без их копии откат
неполный. Подстановка данных предлагается только на макете (`isMockupDs`).

### Вход и права (`auth.js`)

Модель взята у Superset целиком, чтобы макет не обещал порядок доступа, которого в целевой системе
не будет: способ входа — настройка `AUTH_CFG.type` (`db` или `ldap`, это `AUTH_TYPE`), параметры
каталога лежат в `AUTH_CFG.ldap` ключами FAB (`AUTH_LDAP_SERVER`, `AUTH_LDAP_SEARCH`,
`AUTH_LDAP_UID_FIELD`, `AUTH_LDAP_GROUP_FIELD`), роли — `Admin` / `Alpha` / `Gamma`, а выдаёт их
`AUTH_CFG.rolesMapping` (`AUTH_ROLES_MAPPING`: группа LDAP → роль) либо админ руками на экране
«Сотрудники». **Отдельного списка админов в коде нет и быть не должно**: админ — это роль, как в
Superset; список логинов разъехался бы с каталогом в первый же день.

Справочник сотрудников вымышленный (`AUTH_USERS_SEED`), живёт в `localStorage` под
`kobra.auth.users` отдельно от `kobra.state.v1` — сброс шаблонов не должен стирать людей; сессия —
`kobra.auth.session`, настройки — `kobra.auth.cfg`. Из браузера bind в LDAP невозможен, поэтому в
режиме `ldap` Кобра показывает те же экраны и правила на придуманном каталоге — ровно так же, как
рисует придуманные данные для макета. Пароль не проверяется, и на экране входа это написано прямым
текстом.

**Права живут только в трёх функциях**: `canView`, `canEdit`, `canShare`. Экраны спрашивают их и не
заводят своих проверок — иначе правило разъедется по файлам и не переедет на сервер одним куском.
`canView` — админ, владелец, тот, с кем поделились, своя команда, `Alpha` и общие объекты;
`canEdit` — админ, владелец и те, с кем поделились; `canShare` совпадает с `canEdit` (соправитель
добавляет соправителя, как в Superset).

У шаблона, графика и набора есть `ownerLogin`, `team` и `shared`. Имя `ownerLogin`, а не `owner`,
потому что `owner` у набора уже занят ссылкой на дашборд-хозяин (см. «Макет без данных»). Владельца
проставляет `authStampAll()` **из `saveState()`**: через него проходит любой путь создания, и новый
путь не придётся вспоминать. Там же демо-шаблон, его графики и встроенные наборы получают владельца
`kobra` и команду `*` — общие: видны всем, правит админ. Старые объекты без владельца достаются
первому вошедшему: поднимать `v` ради одного поля значит стереть человеку работу.

Экран входа (`renderSignIn`) рисуется вместо приложения: пока не вошли, `boot()` не строит ни
оболочку, ни страницы. Передача доступа — `openShareDialog(obj, что, onChange)`: ввод логина или
почты, поиск в справочнике и **подтверждение с именем, логином, почтой и командой** — логины похожи
(`a.ivanov` и `an.ivanov`), а ошибка тихая. Экраны `openUsersDialog` и `openAuthCfgDialog` — только
для `Admin`.

Граница прототипа, которую нельзя замалчивать: сервера нет, состояние в `localStorage`, и правит его
кто угодно через инструменты разработчика. Это ограничение интерфейса, а не защита данных; настоящая
проверка — в `service/`, там же лежат модели с теми же полями.

### Обмен файлами (`share.js`)

Единственный способ передать работу другому человеку: `.kobra.json` с `kobra: 1`.
`buildExport()` собирает выбранные дашборды, их графики и описания наборов; `kind` файла — `template`
(без строк) или `project` (со строками загруженных наборов). У шаблона загруженный набор по желанию
подменяется схемой (`schemaFromColumns`) — типы колонок настоящие, а значения и диапазоны берутся
по названиям, в реальные данные генератор не подглядывает. Встроенные демо-наборы уезжают ссылкой
(`{id, name, builtin: true}`), их пользовательские метрики — отдельно в `dsMetrics`.
`importPayload(p, mode)` в режиме `copy` выдаёт новые идентификаторы только при совпадении и чинит все
ссылки (`item.chartId`, `chart.datasetId`, `filter.datasetId`), в режиме `replace` перезаписывает
совпавшее по идентификатору. Загруженный набор, приехавший без строк, помечается `fromTemplate` —
его страница просит загрузить файл с такими же колонками.

### Спецификация (`spec.js`)

Превращает согласованный макет в ТЗ. У графика есть необязательный блок `spec`
(`{question, source, refresh, priority, comment}` — поля перечислены в `SPEC_FIELDS`, пустые не
хранятся, см. `normalizeSpec`): правится кнопкой «ТЗ» в шапке конструктора (`openSpecEditor`), виден
в списке графиков, на расчёты не влияет и уезжает в `.kobra.json` вместе с графиком — отдельного кода
в `share.js` для этого не нужно.

Адресат ТЗ — **аналитик данных**, который будет собирать дашборд в целевой BI: так и написано в
первых строках документа («Кому», «Что внутри», «Что от вас нужно»), в названии окна выгрузки и в
пункте меню. Это не косметика: файл открывает не заказчик, и ему нужно сразу понимать задачу.

Поля ТЗ у всех блоков разом правит `openSpecTable(dash)` — карточка на блок (бизнес-вопрос,
источник, обновление, приоритет), счётчик заполненности и галочка «только незаполненные». Раньше
поля правились по одному через конструктор каждого графика: двадцать заходов на двадцать блоков,
хотя заполняет их один человек за один присест. Сохранение идёт через `mutate`, то есть откатывается
как всё остальное. Осторожно: `normalizeSpec` возвращает **null** для пустых полей, а не `{}`.

`buildSpecMd(dash, {author, note})` собирает Markdown по дашборду (или по его черновику в режиме
правки — поэтому принимает и объект, и id), `openSpecDialog` — диалог из меню дашборда со
скачиванием через `downloadFile`. Главное в генераторе: параметры графика печатаются **обходом
декларативной схемы** `VIZ[type].controls` (секции с `tab: 'data'`, плюс из `view` только то, что
отличается от `defaults(ds)`), а подписи и формулы берутся из движка — `exprText`, `metricLabel`,
`metricFormat`, `colLabel`, `describeTimeRange`, `AGGS`, `TIME_GRAINS`, `NUMBER_FORMATS`. Поэтому в
ТЗ те же слова и цифры, что на экране, а новый тип графика описывает себя сам: ничего, кроме
`controls`, добавлять не надо. Новый тип контрола — ветка в `specControlLine`.

### UI-слой (`ui.js`)

Своих фреймворков нет: `h(tag, attrs, ...kids)` строит DOM, перерисовка — через `clear()` + повторный
`paint*()`. Там же `openModal`/`openPop`/`openMenu`/`multiSelect`/`toast`/`confirmDialog`,
обёртки `lsGet/lsSet`, `idb`, `loadScript` и `downloadFile`/`readTextFile` (вся выгрузка в файл идёт
через них). Всё пользовательское в графиках — только через
`h()`/`textContent`; если нужен HTML (Markdown-блоки), он проходит через `marked` + `DOMPurify`
(`renderMarkdown` в `dashboard.js`).

Темы — CSS-переменные в `:root` + `[data-theme="dark"]` + `prefers-color-scheme`; переключатель пишет
`kobra.theme` в localStorage и перерисовывает страницу. Цвета для ECharts берутся из CSS-переменных
через `themeColors()`/`cssv()`, поэтому новые элементы графиков должны брать цвета оттуда, а не
хардкодить. Палитры серий — `COLOR_SCHEMES`, непрерывные шкалы — `SEQ_SCHEMES`.

## `service/` — незаконченный бэкенд

`service/backend/app/core.py` — настройки из переменных окружения `KOBRA_*`, модели метаданных
SQLAlchemy (`kobra_users/connections/datasets/charts/dashboards/settings`), bcrypt-пароли, JWT-сессии
и шифрование строк подключения (Fernet от `KOBRA_SECRET_KEY`). API, фронтенд-адаптера и миграций нет.
У пользователя есть `team`, `role` и `groups`, у наборов, графиков и дашбордов — `owner_login`,
`team` и `shared`: те же поля, что в клиенте, чтобы проверка прав переехала на сервер без переделки
формата. LDAP-клиента тоже пока нет — его место рядом с `AUTH_TYPE`.
Схема `Chart` повторяет форму клиентского графика (`viz` + `params` JSON), `Dashboard.body` — вкладки
и фильтры, так что при правках формата параметров держи эту параллель в голове.
