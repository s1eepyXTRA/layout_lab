# Кобра — прототип конструктора шаблонов для дашбордов

Браузерный прототип в стиле Superset: 13 типов графиков, вкладки, текст, нативные фильтры, кросс-фильтрация, синтетические демо-данные вымышленной розничной сети, загрузка своих CSV/Excel. Всё хранится в браузере (localStorage, загруженные наборы — IndexedDB), а передаётся между людьми файлом `.kobra.json`.

## Структура

```
src/            исходники: styles.css + JS-модули (порядок сборки: data, engine,
                ui, viz, app, dashboard, explore, datasets, schema, autodash, templates,
                guided, assistant, share, spec)
vendor/         библиотеки: ECharts 5.5.1, marked 12.0.2, DOMPurify 3.1.6, SheetJS 0.18.5, PapaParse 5.4.1
build.py        сборка в один HTML-файл
build/
  index.html    онлайн-версия: библиотеки с CDN
  kobra.html    офлайн-версия: всё внутри файла, открывается двойным щелчком
service/        начатая серверная часть (не закончена)
  backend/app/core.py   настройки, модели метаданных, пароли, сессии, шифрование подключений
  backend/app/demo/     демо-данные в CSV для загрузки в базу
  tools/export_demo.js  выгрузка демо-данных из src/data.js
```

## Макет без данных

В сводке готового шаблона три больших числа: что происходит, сколько событий и среднее. Если
какого-то показателя в данных нет, оставшиеся растягиваются на всю ширину — ряд не разваливается.

Главный путь: «Новый шаблон» → «Начать с нуля». Набор данных выбирать не нужно — Кобра порождает его сама и прячет за шаблоном. Блоки добавляются видом визуализации («Столбцы», «Линейный график»), а всё содержательное правится прямо на плитке в режиме «Названия и разрезы»: название блока, название показателя, единица измерения (₽, шт., мин), разрез, количество категорий и их названия.

Правка меняет не подпись на экране, а сам скрытый набор, поэтому переименованная категория называется одинаково во всех блоках, а выбранное в фильтрах переезжает на новые названия. Цифры придуманы детерминированно: при перезагрузке они те же, и у того, кому вы передадите макет файлом, — тоже.

Скрытый набор не виден в разделе «Данные», не предлагается при создании графика и удаляется вместе с шаблоном.

## Готовые шаблоны

«Новый шаблон» → «Готовый шаблон» (или сразу `#/templates`): каталог отчётов, собранных по стандартам визуализации. Готовый шаблон раскладывает работу по трём уровням детализации — сводка (что происходит), разбор (за счёт чего), документы (исходные строки) — и описывает нужные поля ролями, а не именами колонок. Кобра подбирает колонки сама, показывает подбор в окне подтверждения и даёт его поправить; недостающие показатели вроде среднего чека дописывает в набор. Уровни включаются галочками, а любой шаблон можно посмотреть на вымышленных данных до того, как появился файл.

Осторожно со словом «шаблон». То, что человек собирает и правит, — шаблон будущего дашборда: так он называется во всём интерфейсе. «Готовый шаблон» в каталоге — скелет, с которого такой шаблон начинают. В коде, состоянии (`STATE.dashboards`) и маршрутах (`#/d/<id>`) это по-прежнему dashboard: переименовать их значило бы сломать сохранённые состояния и ссылки. В ТЗ, которое уезжает аналитику, речь тоже о дашборде — его по этому шаблону и будут строить.

**Переход по уровням.** Клик по столбцу или сектору фильтрует весь шаблон: выбранное видно на панели фильтров и действует на всех вкладках, а вкладку вы переключаете сами. Своего механизма перехода у Кобры нет намеренно — макет не должен обещать того, чего нет в целевой BI-системе. На первом уровне есть подсказка текстом.

**Простая правка.** Кнопка «Названия и разрезы» в шапке шаблона: под каждым блоком появляется строка с названием и разрезами, а у макета ещё и с показателем, единицей и категориями — без конструктора графика. Разрезов бывает до двух — столько, сколько держит сам график: серии у линии и столбцов, второй уровень у таблицы и древовидной карты, столбцы у сводной, обе оси у тепловой карты; второй включается кнопкой и убирается крестиком. Разрез по дате — это не выбор колонки, а шаг времени: день, неделя, месяц, квартал, год. На макете каждый разрез правится отдельно (название, число категорий, их имена, форма распределения), и если свободных разрезов в придуманных данных не осталось — дописывается новый. У шаблонов на своих и встроенных наборах разрез выбирается из их же колонок, а подписи и категории не правятся: это данные, а не макет. Заголовки, которые придумала Кобра, следуют за разрезом; заданные вручную — остаются. Остальные настройки блока не трогаются, для них есть «Больше настроек».

## Наборы-схемы

Набор данных можно не загружать, а описать: «Данные» → «Описать набор», вставить шапку из Excel или перечислить названия колонок. Тип Кобра угадывает по названию, строки придумывает сама — одни и те же при каждом открытии (детерминированный seed в схеме). Нужно, когда шаблон рисуют до того, как появились данные: заказчик накидывает макет для ТЗ, аналитик — макет на согласование. Шаблон с такими наборами честно подписан: «Это макет, данные вымышленные».

## Черновик шаблона одной кнопкой

На странице набора данных есть «Собрать черновик шаблона». Кобра смотрит на колонки набора и сама
собирает отправную точку: плитки с главными числами, динамику по месяцам, столбцы и круговую по
текстовым разрезам, таблицу с показателями, фильтр периода на последние 12 месяцев и один-два
фильтра-списка. Главную метрику выбирает осмысленно — сначала денежную (`₽` или «руб» в подписи,
формат «рубли»), потом любое другое число, и только если считать нечего — количество строк. Названия
графикам даёт человеческие: «Выручка по филиалам», «Выручка по месяцам». Шаблон сразу открывается
в режиме правки: это заготовка, которую правят и дополняют, а не готовый отчёт.

## ТЗ из согласованного макета

У каждого графика есть поля ТЗ (кнопка «ТЗ» в конструкторе графика): бизнес-вопрос, источник данных, периодичность обновления, приоритет и комментарий. На расчёты они не влияют, зато видны в списке графиков и уезжают вместе с графиком в `.kobra.json`.

**ТЗ пишется для аналитиков данных**, которые будут собирать дашборд в целевой BI-системе: файл
начинается с того, кому он адресован, что внутри и что от аналитика нужно. Поля ТЗ (бизнес-вопрос,
источник, периодичность, приоритет) заполняются у всех блоков сразу — меню шаблона → «Заполнить ТЗ
по блокам», со счётчиком и фильтром «только незаполненные».

Меню шаблона → «Выгрузить ТЗ для аналитиков» собирает из макета готовое задание: вкладки, по каждому графику — тип визуализации, набор данных, метрики с формулами (`SUM(Выручка, ₽) / COUNT_DISTINCT(Номер заказа)`), разрезы с гранулярностью, фильтры, период и лимиты, из оформления — только то, что меняли руками. Отдельным разделом — нативные фильтры шаблона, в конце — список графиков без бизнес-вопроса. Всё печатается теми же подписями, что видно на экране, поэтому ТЗ не расходится с макетом. Если в шаблоне есть набор-схема, в файле стоит пометка, что цифры вымышленные.

## AI-ассистент

Кнопка «AI-ассистент» в шапке шаблона открывает панель сбоку: своя переписка у каждого шаблона. Кнопка есть и при просмотре, и в простой правке, и в конструкторе — в том числе на пустом шаблоне, с которого начинают «с нуля»: там она стоит на самой пустой вкладке, а в шапке её в это время нет, чтобы одинаковых кнопок не было двух. В конструкторе AI-ассистент встаёт на место палитры блоков, а его работа живёт в черновике и отменяется вместе с ним. Человек описывает задачу или свой процесс словами, AI-ассистент предлагает блоки и описание данных; применяется это только по подтверждению и откатывается одним действием вместе с данными и видом блоков.

**Шаблон по описанию.** «Новый шаблон» → «Описать словами»: пишете, что хотите видеть, — Кобра
собирает черновик целиком (вкладки, блоки, придуманные данные под них) и показывает его. Дальше
«Сохранить шаблон», «Доработать» (сказать, что поправить, и пересобрать) или «Отменить». Пока не
сохранили — ничего не записано. При доработке Кобра сама прикладывает к запросу состав черновика и
ошибки блоков, которые не построились, так что описывать поломку словами не нужно. Без настроенного
доступа к модели работает тот же путь через «Скопировать запрос» и «Вставить ответ».

По галочке Кобра собирает **два варианта** — компактный и подробный, — и показывает переключатель:
посмотрите оба и сохраните тот, который ближе. Что выбирают чаще, видно строкой в настройках доступа.

**Бриф** — первый диалог: название шаблона, какие проблемы он решает, за какими показателями следить, нужно ли проваливаться до документов, а под катом — разрезы, период и шаг, с чем сравнивать, кто смотрит и как часто. Форма необязательная: её закрывают крестиком, если макет уже собран и нужно только дополнение. Ответы уходят с каждым запросом отдельным разделом с явными границами, правятся кнопкой «Бриф» и печатаются в выгрузке ТЗ разделом «Зачем этот шаблон».

**Что уходит наружу.** Только названия и типы колонок, формулы показателей и состав шаблона — строк данных нет. Приложить двадцать строк можно отдельной галочкой и только к одному запросу. Кнопка «Что уйдёт» показывает отправляемое целиком до отправки. На макете отправлять нечего: данные там и так придуманы.

**Доступ к модели** задаётся в шестерёнке панели: адрес OpenAI-совместимого эндпоинта, имя модели и токен. Сначала это может быть личный эндпоинт, потом — шлюз компании: меняется настройка, а не код. Токен лежит в этом браузере, поэтому берите персональный, с лимитом и отзываемый.

**Без доступа AI-ассистент тоже работает**: «Скопировать запрос» собирает готовый промпт для внешнего чата, «Вставить ответ» разбирает ответ обратно. В офлайн-сборке (`kobra.html` двойным щелчком) это единственный способ: у файла origin `null`, и шлюзы такие запросы режут.

**Придуманные данные** AI-ассистент не присылает строками — он описывает колонки, а строки порождает Кобра тем же детерминированным генератором. Готовые строки выгружаются в CSV кнопкой в панели.

## Вход и права

Кобра спрашивает, кто вы, до того как показать шаблоны. Способ входа выбирается настройкой, как
`AUTH_TYPE` в Superset: по логину и паролю или по LDAP. Роли те же, что там: **Admin** — всё и
управление сотрудниками, **Alpha** — видит шаблоны всех команд, **Gamma** — свои, своей команды и
те, которыми поделились. Роль даёт сопоставление групп LDAP ролям (`AUTH_ROLES_MAPPING`) или админ
вручную на экране «Сотрудники» — отдельного списка админов нет, админ это роль.

У каждого шаблона, графика и набора есть владелец — тот, кто его создал — и команда. Команда видит
работу коллег **на просмотр**: открыть, покликать фильтры, выгрузить ТЗ. Чтобы коллега мог править,
владелец делится доступом: вводит логин или почту, Кобра показывает, кого нашла — имя, логин, почту,
команду, — и выдаёт доступ только после подтверждения. Получивший доступ правит, удаляет и делится
дальше наравне с владельцем, как соправитель в Superset. Демо-шаблон и встроенные наборы общие:
видно всем, правит админ.

За сервисом коллегу ищет он сам: сперва в своей базе, потом в каталоге компании. Поэтому поделиться
можно и с тем, кто ещё ни разу не входил, — иначе доступ достаётся только тем, кому работа и так
видна, — а подтверждение показывает настоящее имя и команду из каталога, а не один введённый логин.

**Без сервиса это прототип, а не защита.** Состояние лежит в `localStorage` того же браузера, и его
правит любой, кто открыл инструменты разработчика; пароль не проверяется, а bind в LDAP из браузера
невозможен — каталог сотрудников вымышленный, как и данные макета. Права здесь показывают порядок
доступа, чтобы его можно было согласовать и перенести. Если страницу отдаёт сервис (см. «Бэкенд»),
вход и права проверяет он: пароль — по своей базе или bind-ом в каталог, права — теми же тремя
правилами, а клиентские проверки остаются только чтобы прятать кнопки.

## Тесты

```bash
node test/run.js            # всё
node test/run.js auth.test.js
npx -p typescript@5.6.3 tsc -p kobra/jsconfig.json   # типы по JSDoc, из корня репозитория
```

Зависимостей нет: `test/load.js` грузит `src/*.js` в контекст `vm` тем же порядком, что сборка, и
отдаёт их функции. Проверяется ядро — то, на чём держатся обещания продукта: отношения считаются на
любом уровне группировки, относительные периоды — от последней даты в данных, один seed даёт одни и
те же придуманные строки, и таблица прав целиком. Плюс три проверки самой сборки: все файлы `src/`
перечислены в `ORDER`, синтаксис цел, `build/` собран из нынешних исходников. Интерфейс — руками.

Типы живут в JSDoc (`src/types.js`), проверяются компилятором TypeScript, но самого TypeScript в
проекте нет: сборка не меняется, зависимостей не прибавляется, а редактор подсказывает и ругается
как на типизированном коде.

## Обмен файлами

«Экспорт в файл» (меню-шестерёнка в шапке, меню шаблона или список шаблонов) складывает шаблоны, графики и описания наборов в один `.kobra.json`:

- **Шаблон** — только структура. Строки загруженных файлов не вкладываются; по желанию Кобра подменит их вымышленными, чтобы графики не были пустыми.
- **Проект** — вместе со строками загруженных наборов. Такой файл несёт настоящие данные, с ним аккуратнее.

«Импорт из файла» показывает, что внутри, и при совпадении идентификаторов спрашивает: добавить копией или заменить свои версии.

## Как запустить у себя

Ставить нечего: ни npm, ни зависимостей, ни базы. Нужен только браузер, а для сборки — Python 3
(на Windows команда называется `py`, а не `python3`).

**Самый быстрый способ — ничего не собирать.** В репозитории уже лежит готовая сборка:
откройте `kobra/build/kobra.html` двойным щелчком. Внутри файла все библиотеки, интернет не нужен.

**Собрать из исходников:**

```bash
git clone https://github.com/s1eepyXTRA/layout_lab
cd layout_lab/kobra
python3 build.py           # build/index.html  — библиотеки с CDN, нужен интернет
python3 build.py offline   # build/kobra.html  — всё внутри файла, открывается двойным щелчком
```

**Запустить `index.html` через локальный сервер:**

```bash
python3 -m http.server 8777 --directory build
```

Дальше `http://localhost:8777/index.html`. Онлайн-версии нужен именно `http://`: страницы
переключаются через `history.pushState`, а с `file://` браузер такие переходы запрещает. Офлайн-версия
(`kobra.html`) работает и так, и так.

После правок в `src/` пересоберите обе сборки — в репозитории лежат обе, иначе они разъедутся.
Единственная доступная проверка кода — синтаксис: `for f in src/*.js; do node --check "$f"; done`.

Без сервиса всё, что вы сделаете, хранится в этом браузере: шаблоны и графики — в localStorage
(ключ `kobra.state.v1`), строки загруженных файлов — в IndexedDB. Другой браузер или режим инкогнито
начнут с чистого демо; «Настройки» → «Сбросить всё к начальному состоянию» возвращает исходный вид.

## Бэкенд

Кобра работает и без сервера, и с ним — `service/backend/`. Если страницу отдаёт сервис, шаблоны и
наборы живут в базе, вход и права проверяет он, а большие файлы разбирает воркер. Что сервис должен
делать — `openspec/specs/server-storage`, `server-auth` и `deployment`; почему именно так —
`openspec/changes/archive/2026-10-29-server-backend/design.md`.

Нужны Python 3 и Postgres. Базу проще взять в Docker:

```bash
docker run -d --name kobra-pg -e POSTGRES_USER=kobra -e POSTGRES_PASSWORD=kobra -e POSTGRES_DB=kobra -p 5433:5432 postgres:16-alpine
```

Окружение и зависимости (на Windows вместо `python3` — `py`, а вместо `.venv/bin` — `.venv/Scripts`):

```bash
cd kobra/service/backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Адрес базы и ключ шифрования задаются окружением; без ключа сервис честно предупреждает, что
работает на ключе для разработки:

```bash
export KOBRA_DATABASE_URL="postgresql+psycopg://kobra:kobra@localhost:5433/kobra"
export KOBRA_SECRET_KEY="что-угодно-длинное-для-разработки"
```

Схема базы приводится в порядок Alembic-ом, запуск — uvicorn-ом:

```bash
.venv/bin/python -m alembic upgrade head     # накатить схему (откат: alembic downgrade base)
.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

Проверить, что поднялось:

```bash
curl http://localhost:8000/healthz   # {"status":"ok"} — процесс жив
curl http://localhost:8000/readyz    # {"status":"ready"} — база доступна; без базы 503
```

Пробы отвечают на разные вопросы: `/healthz` не ходит в базу намеренно, иначе короткая
недоступность базы перезапускала бы все экземпляры сервиса.

Тесты бэкенда идут против настоящего Postgres (отдельная база `kobra_test`, создаётся сама):

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

## Развёртывание

Весь сервис — один образ: внутри собранный интерфейс и API. Интерфейс собирается офлайн-вариантом,
со всеми библиотеками внутри файла: в закрытом контуре до CDN не достучаться, и сборка с внешними
ссылками открылась бы пустым экраном.

**Окружение разработки одной командой** (сервис, воркер, Postgres, Redis, миграции):

```bash
cd kobra/service/backend
docker compose up --build
```

Дальше `http://localhost:8000`, вход `admin` / `admin`. Демо-наборы загружаются сами
(`KOBRA_LOAD_DEMO=1`). Каталог LDAP для проверки входа поднимается отдельно:
`docker compose --profile ldap up`.

**Образ отдельно:**

```bash
docker build -f kobra/service/backend/Dockerfile -t kobra:dev .   # из корня репозитория
docker run -p 8000:8000 -e KOBRA_DATABASE_URL=... -e KOBRA_SECRET_KEY=... kobra:dev
```

Один образ — три роли, выбирает команда: `api` (по умолчанию), `worker` (разбор загруженных файлов),
`migrate` (прокатить схему и выйти).

**В Kubernetes** — чартом из `kobra/service/deploy/helm`, см. его README. Postgres и Redis внешние;
миграции катит job перед обновлением, а не каждый под.

**Переменные окружения:**

| Переменная | Зачем |
|---|---|
| `KOBRA_DATABASE_URL` | Postgres: `postgresql+psycopg://user:pass@host:5432/kobra` |
| `KOBRA_REDIS_URL` | Redis: кэш, очередь, лимиты. Без него сервис работает медленнее, но работает |
| `KOBRA_SECRET_KEY` | Подпись сессий и шифрование строк подключения. Не задан — сервис честно предупредит |
| `KOBRA_AUTH_TYPE` | `db` или `ldap` |
| `KOBRA_LOAD_DEMO` | Загрузить демо-наборы при первом старте (`1`/`0`) |
| `KOBRA_ADMIN_USER`, `KOBRA_ADMIN_PASSWORD` | Первый админ, если база пустая |
| `KOBRA_MAX_UPLOAD_ROWS`, `KOBRA_MAX_FILE_MB` | Пределы загрузки |
| `KOBRA_MIGRATE_ON_START` | Прокатить миграции при старте контейнера (для разработки) |

Проверить, что поднялось: `/healthz` — процесс жив, `/readyz` — база доступна и сервис готов.

## Ограничения прототипа

- Без сервиса данные и шаблоны живут только в браузере, где открыт файл, и переносятся экспортом
  в `.kobra.json`. Если страницу отдаёт сервис (см. «Бэкенд»), состояние уезжает в базу, а вход и
  права проверяет сервер.
- Выгрузки самих данных нет: ни картинок, ни Excel, ни PDF — есть «Посмотреть данные» и экспорт шаблонов.
- Относительные периоды («последние 12 месяцев») считаются от последней даты в данных: для демо-данных это 31.08.2026, для набора-схемы — конец его периода.
- У наборов-схем период фиксируется при создании, иначе цифры менялись бы каждый день.
