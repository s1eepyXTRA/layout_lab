# Кобра — сервис

Бэкенд «Кобры»: тот же интерфейс, что открывается двойным щелчком из файла, но за ним база, вход и
расчёты. Один образ отдаёт и интерфейс, и API — версии не могут разойтись, это одна строка в теге.

Этот документ — про запуск и эксплуатацию. Почему решения именно такие — `CLAUDE.md` в корне и
спецификации в `openspec/specs/` (`server-storage`, `server-auth`, `deployment`, `service-operations`).

## Быстрый запуск

Всё окружение одной командой — сервис, воркер, Postgres, Redis, миграции:

```bash
cd kobra/service/backend && docker compose up --build
```

Откроется `http://localhost:8000`, вход `admin` / `admin`. Каталог LDAP для разработки — отдельным
профилем: `docker compose --profile ldap up -d ldap`.

Без Docker, против своей базы:

```bash
docker run -d --name kobra-pg -e POSTGRES_USER=kobra -e POSTGRES_PASSWORD=kobra \
  -e POSTGRES_DB=kobra -p 5433:5432 postgres:16-alpine
python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
export KOBRA_DATABASE_URL="postgresql+psycopg://kobra:kobra@localhost:5433/kobra"
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m uvicorn app.main:app --port 8000
```

Тесты — `python -m pytest -q`, они поднимают отдельную базу `kobra_test`. Проверки против каталога
LDAP пропускаются, если каталог не поднят.

Драйвер — psycopg 3 (`postgresql+psycopg://`), не psycopg2: у второго нет колёс под свежий Python.

## Один образ, три роли

Роль выбирает команда контейнера:

| Команда | Что делает |
|---|---|
| `api` (по умолчанию) | веб-сервис: интерфейс и API |
| `worker` | воркер очереди: разбирает загруженные файлы |
| `migrate` | катит миграции и выходит; затем создаёт индексы по времени у наборов, залитых раньше (`KOBRA_INDEX_DATASETS=0` выключает) |

Миграции катит **отдельный job до обновления** подов, а не каждый под при старте: иначе два пода
столкнутся на одной базе. Для разработки есть `KOBRA_MIGRATE_ON_START=1`.

Образ собирается из корня репозитория:

```bash
docker build -f kobra/service/backend/Dockerfile -t kobra:dev .
```

## Переменные окружения

Обязательные:

| Переменная | Зачем |
|---|---|
| `KOBRA_DATABASE_URL` | `postgresql+psycopg://user:pass@host:5432/kobra` |
| `KOBRA_SECRET_KEY` | подпись сессий и шифрование строк подключения. Не задан — сервис честно предупредит и возьмёт ключ для разработки |

Остальное по необходимости:

| Переменная | Умолчание | Зачем |
|---|---|---|
| `KOBRA_REDIS_URL` | `redis://localhost:6379/0` | кэш, очередь разбора, пределы частоты, отзыв сессий |
| `KOBRA_AUTH_TYPE` | `db` | `db` — пароль по своей базе, `ldap` — bind в каталог |
| `KOBRA_ADMIN_USER`, `KOBRA_ADMIN_PASSWORD` | `admin` / `admin` | первый админ, если база пустая |
| `KOBRA_SESSION_DAYS` | `14` | срок сессии |
| `KOBRA_LOAD_DEMO` | `1` | демо-наборы при первом старте |
| `KOBRA_MAX_UPLOAD_ROWS` | `50000` | предел строк в наборе: разбор останавливается на нём, набор остаётся рабочим |
| `KOBRA_MAX_FILE_MB` | `512` | предел размера файла |
| `KOBRA_QUERY_TIMEOUT_SEC` | `120` | `statement_timeout` для расчётов |
| `KOBRA_CONNECT_TIMEOUT_SEC` | `3` | без него `/readyz` не отвечает «не готов», а висит |
| `KOBRA_DB_POOL`, `KOBRA_DB_POOL_OVERFLOW` | `10`, `20` | пул соединений **на под** |
| `KOBRA_THREADPOOL` | `30` | потоки под синхронные маршруты; сервис не даст поставить больше, чем соединений |
| `KOBRA_SLOW_QUERY_MS` | `2000` | порог, после которого расчёт попадает в лог |
| `KOBRA_RATE_QUERY`, `KOBRA_RATE_WRITE`, `KOBRA_RATE_UPLOAD` | `600`/мин, `300`/мин, `20`/5 мин | пределы частоты на человека |
| `KOBRA_RATE_LIMIT_LOGIN` | `10` | попытки входа с одного адреса |
| `KOBRA_WORKER_CONCURRENCY` | `2` | сколько файлов воркер разбирает разом |

Пул считается **на число подов**:

```
(KOBRA_DB_POOL + KOBRA_DB_POOL_OVERFLOW) × replicas + воркер + job миграций < max_connections базы
```

При умолчаниях и двух подах это 60 соединений из обычных 100. С ростом `replicas` пул уменьшают, а не
оставляют как есть.

## Наблюдение

| Адрес | Что отвечает |
|---|---|
| `/healthz` | процесс жив. Намеренно не ходит в базу: иначе короткая недоступность базы перезапустила бы все поды вместо того, чтобы снять с них трафик |
| `/readyz` | готов принимать запросы: проверяет базу, при отказе отдаёт 503 с причиной |
| `/metrics` | метрики в формате Prometheus, без входа |

Что считается: запросы и время по шаблонам маршрутов, расчёты (с попаданиями в кэш), медленные
расчёты, загрузки и строки, отказы по частоте, неудавшиеся отзывы сессий, записи поверх чужой правки,
занятость пула соединений и выход за него, длина очереди разбора.

В метриках нет ничего персонального — ни логинов, ни названий шаблонов и наборов: адрес открыт
системе наблюдения, и такой ответ не должен быть выгрузкой справочника. Счётчики живут в памяти
процесса и теряются при перезапуске пода; сумму по подам складывает система наблюдения. Три счётчика
растит воркер (разобранные файлы, упавшие, строки) — они идут через Redis, потому что процессы
разные.

Расчёт дольше `KOBRA_SLOW_QUERY_MS` попадает в лог `kobra.query` с временем, набором и текстом
запроса — по нему запрос можно воспроизвести руками.

## Резервные копии

Копировать нужно **обе схемы**: `public` (шаблоны, графики, описания наборов, сотрудники) и
`kobra_uploads` (строки загруженных файлов). Обычный `pg_dump` базы включает обе:

```bash
pg_dump -U kobra -d kobra -Fc -f kobra.dump
```

Восстановление на пустую базу:

```bash
createdb -U kobra kobra_restore
pg_restore -U kobra -d kobra_restore --no-owner kobra.dump
```

Проверка, что восстановилось не на словах: поднять сервис на этой базе, войти, открыть шаблон,
построенный на **загруженном** наборе, и увидеть цифры. Схема загрузок проверяется только так —
список шаблонов откроется и без неё.

Строки наборов живут в таблицах, которые создаются в рантайме (`kobra_uploads.ds_<id>`) и миграциями
не управляются. Поэтому метаданные и строки могут разойтись, и это не теоретический случай: база,
восстановленная без `kobra_uploads`, даёт работающий сервис, в котором наборы помечены «строки не
найдены» и просят файл заново. Как аварийный режим это допустимо, как план — нет.

После восстановления стоит прокатить роль `migrate`: она создаст индексы по времени у наборов, если
их почему-то нет.

## Частые отказы

| Признак | Причина |
|---|---|
| `/readyz` отдаёт 503 с текстом про базу | нет связи с Postgres или не прокатаны миграции |
| Сервис поднялся, но вход отвечает «каталог недоступен» (503) | `KOBRA_AUTH_TYPE=ldap`, а до каталога нет связи. Неверный пароль — это 401, и путать их нельзя |
| Загрузка файла висит в «готовится» | воркер не запущен или лежит Redis. Длина очереди видна в метрике `kobra_ingest_queue` |
| Загрузка отвечает «сервис недоступен» сразу | Redis недоступен: честный отказ лучше, чем принять файл и ничего не сделать |
| Расчёт отвечает 404 «Строки набора не найдены» | есть описание набора, нет его таблицы — см. раздел про резервные копии |
| Расчёт отвечает 409 «Набор ещё готовится» | файл принят, разбор не закончился |
| 429 с «повторите через N с» | предел частоты. Пределы — на человека, см. `KOBRA_RATE_*` |
| Новый под не получает соединений | пул умножился на число подов и вышел за `max_connections` базы |
| В интерфейсе «не сохранено» и 409 | объект изменился в другом месте: клиент показывает, кто и когда записал чужую версию, и даёт выбрать — перечитать или записать своё поверх |
| В логе «Запись поверх чужой правки» | человек выбрал своё поверх чужого (`?overwrite=1`). Это не ошибка, но чужая правка пропала — счётчик `kobra_overwrites_total` |
| Автогенерация миграции предлагает удалить `ds_*` | так не должно быть: в `alembic/env.py` стоит `include_object`, который прячет таблицы наборов. Если предлагает — фильтр сломали |
