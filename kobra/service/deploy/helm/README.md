# Чарт «Кобры»

Разворачивает сервис: веб-под с интерфейсом и API, воркер очереди и job миграций.

Postgres и Redis **внешние** — чарт их не ставит. База с данными не должна исчезать вместе с релизом
приложения, а подчарт с базой однажды снесут командой `helm uninstall`.

## Установка

```bash
helm upgrade --install kobra kobra/service/deploy/helm \
  --set image.repository=registry.company.local/kobra \
  --set image.tag=0.1.0 \
  --set secrets.databaseUrl='postgresql+psycopg://kobra:пароль@postgres:5432/kobra' \
  --set secrets.secretKey='длинный-случайный-ключ' \
  --set redis.url='redis://redis:6379/0' \
  --set ingress.enabled=true --set ingress.host=kobra.company.local
```

Пароли лучше не писать в командной строке: положите их в Secret заранее и укажите
`--set secrets.existingSecret=kobra-secrets` (ключи внутри — `databaseUrl` и `secretKey`).

## Что происходит при установке и обновлении

1. **Job миграций** (`pre-install,pre-upgrade`) приводит схему к нужной версии и завершается. Поды
   стартуют уже на новой схеме; катить миграции каждым подом нельзя — они столкнутся друг с другом.
2. Поднимается **Deployment сервиса** (`replicas` штук). Готовность — `/readyz`: он проверяет базу,
   и под не берёт трафик, пока она недоступна.
3. Поднимается **воркер**: разбирает загруженные файлы. Файл он берёт из базы, а не с общего диска,
   поэтому том с `ReadWriteMany` не нужен.

Откат — `helm rollback`. Он вернёт образ, но **не схему**: если новая версия катила миграцию,
откатывать её нужно отдельно (`kubectl run … migrate`, `alembic downgrade`). Поэтому необратимые
шаги (удаление колонок) разносятся на два релиза.

## Переменные

Всё, что настраивается, — переменные `KOBRA_*` в `values.yaml`, секция `env`. Полный список, смысл и
умолчания — в `kobra/service/backend/README.md`. Два значения приходят из Secret: строка подключения
и ключ шифрования.

Проба жизни (`/healthz`) намеренно не ходит в базу: иначе короткая недоступность базы перезапустила
бы все поды разом вместо того, чтобы просто снять с них трафик.

### Пул соединений и число подов

`KOBRA_DB_POOL` и `KOBRA_DB_POOL_OVERFLOW` — пул **на каждый под**, а не на сервис. Считать так:

```
(KOBRA_DB_POOL + KOBRA_DB_POOL_OVERFLOW) × replicas + воркер + job миграций < max_connections базы
```

При умолчаниях 10 + 20 и двух подах это 60 соединений из обычных у Postgres 100 — третий под уже за
гранью. Значит, с ростом `replicas` пул уменьшают, а не оставляют как есть: иначе новый под не
получит соединений, и это будет выглядеть как «сервис сломался после масштабирования».

`KOBRA_THREADPOOL` — потоки под синхронные маршруты; сервис сам не даёт поставить их больше, чем
соединений в пуле. Потоков больше — значит часть из них ждёт очередь к пулу, а не базу, и график
времени ответа врёт о причине.
